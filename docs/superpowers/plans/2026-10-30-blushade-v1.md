# BluShade V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Convert the existing ProClubs-API project into a modular, restart-safe BluShade football-operations platform for Birmingham City while preserving working infrastructure and production safety.

**Architecture:** Reuse the existing Railway/Discord project and CommonJS Node runtime. Introduce `src/blushade` modules behind feature flags, add CI first, then PostgreSQL-backed repositories and migration tooling, then move stats/matchday/scouting/club-operations workflows into the new architecture. Legacy RT/CrownFC code is retired only after dependency checks and parity tests.

**Tech Stack:** Node.js CommonJS, discord.js 14, PostgreSQL, Node test runner, Sharp/SVG/HTML deterministic rendering, Railway, GitHub Actions.

**Spec:** Final BluShade master specification supplied in the project conversation on 2026-10-30.

## Global Constraints
- Preserve existing GitHub repo, Railway project, Discord app identity and existing secrets.
- Work only on `blushade/refactor-v1` until reviewed; production `main` remains untouched.
- Use `America/New_York` for football-operation time rules.
- Never expand the legacy `reporterBot.js` with new BluShade product logic.
- NACL/MPL remains authoritative where source data exists; BluShade-derived rankings are explicitly labeled derived.
- Consequential football decisions always require human confirmation.
- Persistent scheduled operations must be restart-safe and idempotent.
- Legacy RT/CrownFC deletion occurs only after dependency validation and replacement coverage.

## Review Focus
1. Railway restart during an open MatchSession must not duplicate panels, jobs or DMs.
2. NACL partial/failing refresh must preserve the last-known-good snapshot and never create false rank movement.
3. Discord role/message/event deletion must fail safe and support owner repair/reconciliation.
4. Concurrent managers editing a lineup/case must not silently overwrite each other.
5. Migration failure must leave existing production state recoverable.
